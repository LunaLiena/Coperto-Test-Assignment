# Стоп-лист смены

Тестовое задание Coperto — панель стоп-листа кухни: менеджер зала видит меню
смены, фильтрует его по цеху и статусу, ставит позиции в стоп-лист или
снимает их со стопа.

## Как запустить локально

```bash
npm install
npm run dev
```

Приложение поднимется на `http://localhost:3000`. Отдельный бэкенд не
нужен — GET/POST-запросы обрабатывают route handler'ы Next.js
(`app/api/**`), данные живут в памяти процесса.

Проверка линта, типов, тестов и форматирования:

```bash
npm run lint
npm run typecheck
npm run test
npm run format
```

CI (`.github/workflows/ci.yml`) на каждый push/PR в `main` прогоняет те же
четыре шага (lint → typecheck → test → build) в GitHub Actions. Workflow
использует `npm install`, а не `npm ci`, потому что репозиторий сдаётся без
закоммиченного `package-lock.json` — после первого локального
`npm install` рекомендуется закоммитить лок-файл и тогда переключить
workflow на `npm ci` для воспроизводимых сборок.

### Граница сервер/клиент

- `app/page.tsx` — серверный компонент. Он ничего не рендерит сам по себе
  сверх обёртки: единственная его задача — прочитать `searchParams`, чтобы
  разбор URL был явно виден на границе входа в приложение, и передать
  управление клиентскому дереву.
- Всё, что дальше (`StopListPage` и его дети) — клиентские компоненты,
  потому что вся логика экрана интерактивна: TanStack Query, Zustand,
  `useSearchParams/useRouter`, React Hook Form, Framer Motion — всё это
  либо хуки, либо требует браузерного рантайма.
- `layout.tsx` остался серверным: шрифт (`next/font`) и метаданные не
  требуют клиента, а `Providers`/`ToastContainer` подключены как отдельные
  клиентские островки внутри серверного дерева.
- В route handler'ах нет ничего, кроме работы с `server/menu-store.ts` —
  они не импортируют ничего из `features/**/ui`, а `features/**/model`
  переиспользуется и в них (общая Zod-схема).

## Архитектурные решения

- **Один ключ кэша на весь список** (`menuKeys.list()`), а не отдельный
  ключ под каждую комбинацию фильтров. Датасет маленький, сервер не
  фильтрует данные — фильтрация происходит на клиенте через `useMemo` над
  единым кэшем. Это упрощает оптимистичные обновления: патчить нужно ровно
  одну запись кэша, а не думать, в каких из N списков сейчас лежит позиция.
  Это единственное осознанное отступление от структуры, подсказанной в
  задании (там пример мутации принимает `filtersKey`).
- **Единая Zod-схема** (`stopItemFormSchema`) валидирует форму (React Hook
  Form) и переиспользуется как основа для `stopItemPayloadSchema` на
  сервере — правило `validateUntil` (шаг 15 минут, не более 24 часов
  вперёд) живёт в одном месте и не может разойтись между клиентом и API.
- **Мутации завязаны на единственный инстанс хука на весь список**
  (`useStopItem`/`useResumeItem` вызываются один раз в `StopListPage`, а
  не на каждую строку), поэтому `mutation.isPending` вместе с
  `mutation.variables.id` однозначно говорят, какая строка сейчас
  "сохраняется" — не нужен отдельный стор для отслеживания pending-строк.
- **Zustand хранит только UI-состояние** (какая позиция открыта в панели,
  очередь тостов) — серверные данные туда не попадают вообще, они целиком
  в кэше TanStack Query. Так однозначно исключено дублирование источников
  правды.
- **Повторная постановка = тот же route handler.** Открытие панели на уже
  застопленной позиции переиспользует `POST /stop` с предзаполненной
  формой — отдельного endpoint'а для редактирования нет, т.к. в задании он
  не описан, а результат (обновить reason/until) идентичен.

## Допущения (там, где задание не уточняло)

- Задержка и ~20%-вероятность ошибки применены и к `stop`, и к `resume` —
  в задании про это явно сказано только применительно к оптимистичному
  обновлению в общем, я распространил поведение на оба route handler'а.
- In-memory стор на Vercel serverless не переживает холодный старт функции
  — это ожидаемо и описано в комментарии в `server/menu-store.ts`; в
  dev-режиме стор дополнительно кладётся в `globalThis`, чтобы не
  сбрасываться при hot-reload.
- `<input type="datetime-local">` со `step={900}` — при часовых поясах со
  смещением не кратным 15 минутам (например, UTC+5:30) шаг может визуально
  вести себя иначе; серверная валидация всё равно проверяет фактический
  timestamp, так что некорректное значение будет отклонено, а не тихо
  принято.

## Тесты

Один осмысленный юнит-тест (бонус из задания, `features/stop-list/model/use-stop-item.test.tsx`),
проверяющий именно оптимистичное обновление и откат `useStopItem`:

- сразу после `mutate(...)` кэш TanStack Query уже показывает `status.kind === 'stopped'`,
  не дожидаясь ответа "сервера" (мок `fetch`);
- при смоделированном отказе сервера (`ok: false`) кэш откатывается обратно к
  `status.kind === 'available'`;
- отдельным кейсом проверено, что при успешном ответе оптимистичное состояние остаётся как есть.

`fetch` замокан детерминированно (`vi.stubGlobal('fetch', ...)`), а не через
реальную ~20%-ную вероятность из route handler'а — так тест не флакует.
